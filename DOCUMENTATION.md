# HAQMS — Fix Documentation

## Issues Identified
See triage table in session notes. Full list covers: security vulnerabilities (SQL injection,
broken access control, plaintext password logging, JWT misconfiguration), performance issues
(N+1 queries, sequential aggregates, race condition), database problems (in-memory pagination,
missing constraints/indexes), and frontend issues (memory leak, hardcoded URLs, NULL crash).

## Optimizations Performed

**Pattern: per-row queries → set-based operations.** Two separate endpoints shared the same root cause: running a query (or queries) per row in a result set rather than asking the database to aggregate across all rows in one pass. This is the defining N+1 smell, and fixing it consistently across both endpoints is the engineering decision — not just two isolated wins.

| # | Commit | What was optimized |
|---|--------|-------------------|
| 1 | perf(appointments): eliminate N+1 query with Prisma include | `GET /api/appointments` — **per-row queries eliminated**. findMany + per-row findUnique loop (2 queries per appointment) replaced with single findMany + include. **13 → 3 queries** on seed data (verified with Prisma `$on('query')` listener). Response shape unchanged. |
| 2 | perf(doctors): parallelise stats aggregates with Promise.all | `GET /api/doctors/stats` — four independent DB calls ran sequentially. Wrapped in `Promise.all`. On a local warm DB the wall-clock difference compresses to noise; the real gain scales with RTT — at 10ms per query on a production DB, sequential ≈ 40ms, parallel ≈ 10ms (bounded by the slowest single query). `debugInfo.executionTimeMs` and internal notes removed — timing instrumentation is not a client concern. |
| 3 | perf(reports): replace per-doctor query loop with set-based groupBy aggregation | `GET /api/reports/doctor-stats` — **per-row queries eliminated**. Original: `1 + 5×N` sequential queries (5 count/findMany calls per doctor) plus a planted `setTimeout(80ms)` per doctor. With 5 doctors: 26 queries + ~400ms artificial sleep = **~435ms** measured. Rewrite: 3 total queries (`doctor.findMany`, `appointment.groupBy({ by: ['doctorId','status'] })`, `queueToken.groupBy({ by: ['doctorId'] })`), all in `Promise.all`, results merged in JS. **~435ms → ~20ms warm** on localhost — the dramatic gap is real because the sleep was a fixed per-doctor cost. On production without the sleep, the structural gain is `(5N queries serialized) → 3 queries regardless of N` — the same RTT multiplier argument as fix #1. Zero-appointment doctors preserved via merge against full doctor list with `|| 0` defaults. `timeTakenMs` removed from response payload. |
| 4 | perf(patients): push pagination, filtering, and search into the DB query | `GET /api/patients` — **in-memory pagination eliminated**. Original: `findMany()` loaded the entire patients table into Node memory, then filtered in JS (`.filter()`), then sliced (`.slice()`). Every list request transferred all rows across the DB connection regardless of search terms or page size. Rewrite: `where` built conditionally from `search` (Prisma `OR` across name/phoneNumber/email with `contains`) and `gender` (only added when truthy and not `'All'`); `skip`/`take` pushed into `findMany`; `count({ where })` runs in `Promise.all` alongside the page query — no `$transaction` because the tiny read-skew window on count (off-by-one if a patient is inserted between queries) is acceptable for a paginated list and a transaction at Read Committed would not prevent it anyway. Response shape is byte-identical. **Also**: three `details: error.message` / bare `error.message` leaks in the same file (GET list, GET `/:id`, POST) standardized to `console.error` + generic message, consistent with the established pattern. |

## Major Decisions & Reasoning (continued)

- **Standard error-handling pattern — applied consistently across the codebase**: `console.error` the full error server-side; return only `{ error: '<generic message>' }` to the client. This pattern was established on the first security fix and then applied to every subsequent route and handler touched: `middleware/auth.js`, `routes/auth.js`, `routes/doctors.js`, `routes/patients.js`, `routes/queue.js`, and finally the global error handler in `index.js` (six separate files). The consistency is the engineering story — not six isolated fixes but one standard enforced codebase-wide. The global handler is the last backstop: it previously had a `NODE_ENV === 'development'` gate on the stack field, which is a footgun — wrong env config in production leaks stacks. Removed unconditionally.
- **`config.js` as centralised environment validation**: "Centralised environment validation. Reads and validates required env vars at module load; throws loudly if any are missing." Both `JWT_SECRET` and `CORS_ALLOWED_ORIGINS` are validated here. `dotenv.config()` must run before `require('./config')` in `index.js` — this is enforced by load order and noted with a comment. Adding a new required env var means adding one line to `config.js`; the server will refuse to boot without it.
- **CORS origins from env, not hardcoded**: `cors({ origin: ['http://localhost:3000'] })` hardcoded would break on deployment (different host). `CORS_ALLOWED_ORIGINS` is a comma-separated env var parsed at boot time — `http://localhost:3000` locally, the deployed frontend URL in production. Misconfiguration fails loudly at startup rather than silently accepting all origins or silently rejecting the deployed frontend.

## Remaining Known Issues

- **`react-hooks/exhaustive-deps` warning on queue page interval effect**: `fetchQueueData` is not listed in the `useEffect` deps array. The correct full fix is to wrap `fetchQueueData` in `useCallback` (with its own stable deps) and then add it to the effect deps — left out of scope for this bug. The warning is intentional signal; suppressing it with `eslint-disable` would hide the incomplete fix. The interval itself is correct: it fires every 3s, cleans up on unmount, and `setRefreshCount(prev => prev + 1)` already uses the functional updater form so it doesn't close over stale state.
- **`DELETE /api/patients/:id` 500s for patients with appointments** — admin delete now correctly enforces auth, but `prisma.patient.delete()` will throw a FK constraint error for any patient who has linked appointments or queue tokens (i.e., most real patients). Proper fix requires one of: (a) cascade delete (dangerous — silently wipes appointment history); (b) soft-delete with a `deletedAt` flag (preserves history, preferred for medical records); or (c) block the delete with a clear 409 response and require the caller to reassign or cancel linked records first. Left out of scope for this assessment.

## Major Decisions & Reasoning
- **Schema reconstructed, not invented**: every field type and relation was derived from actual
  Prisma client calls in the route files, not guessed. No extra fields added.
- **Standard error-handling pattern (all routes)**: `console.error` the full error server-side;
  return only `{ error: '<generic message>' }` to the client — no `details`, `sqlMessage`,
  `databaseError`, `errorStack`, or any field derived from `error.message`. Prisma errors can
  leak table/column names; Express stack traces expose file paths. Applied consistently on every
  route touched.
- **No `@@unique([doctorId, date, tokenNumber])` on QueueToken yet**: Prisma cannot enforce a
  date-part extract in a schema constraint. The race condition (bug #9) will be fixed with a
  DB transaction in application code, not a schema constraint.
- **No partial unique index on Appointment yet**: `@@unique([doctorId, appointmentDate]) WHERE
  status != 'CANCELLED'` is a partial index — not expressible in Prisma schema. Will be added
  as raw SQL in a dedicated migration when bug #16 is tackled.
